What does kubectl create deployment nginx-deployment --image=nginx do?
This command instructs your Kubernetes cluster 
to create a new Deployment resource named nginx-deployment using the official Nginx web server image.

Breakdown of the Command Parts:
kubectl: The command-line tool used to communicate with and manage Kubernetes clusters.

create deployment nginx-deployment: Tells Kubernetes 
to generate a Deployment object. 
A Deployment manages a replica set of pods behind the scenes, 
ensuring that the application stays running, handles updates smoothly, and can scale up or down.

--image=nginx: Specifies the container image to download and run inside the deployment's pods. 
By default, it pulls the standard nginx image from Docker Hub.

Once you run this command, Kubernetes will pull the Nginx container image 
and start running it inside a Pod managed by your new deployment. 
You can check its status afterward by running kubectl get deployments or kubectl get pods.

When creating a deployment is it possible to indicate the initial number of Pods replicas ?

Yes, it is completely possible to specify the initial number of Pod replicas when creating a deployment. 
You can do this either imperatively via the command line or declaratively using a configuration file.

Method 1: Using the Command Line Flag (--replicas)
You can pass the --replicas (or short flag -r) directly when running the kubectl create deployment command:

$ kubectl create deployment nginx-deployment --image=nginx --replicas=3

What it does: This creates the nginx-deployment with 3 running instances (pods) 
of the Nginx container right from the start. 
If you omit this flag, Kubernetes defaults to creating 1 replica.

Method 2: Defining it in a YAML Manifest File
If you prefer a declarative approach using a YAML configuration file, you can set the replica count inside the spec section:

YAML::
//**-- --**//
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3   # <-- Specify your initial number of Pod replicas here
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx
//**++ ++**//

You can then apply this configuration using:

$ kubectl apply -f deployment.yaml

##-- --##
Why is this happening?
You are running into two related issues caused by a conflict between 
how the deployment was originally created and what your YAML file specifies:

Missing Last-Applied Annotation:
Because you originally created the deployment imperatively using kubectl create deployment, 
Kubernetes did not attach the kubectl.kubernetes.io/last-applied-configuration annotation that kubectl apply relies on 
to track declarative state. 
While kubectl apply attempts to automatically patch this missing annotation, 
it leads straight into the second, blocking error.

The spec.selector Field is Immutable:
When you ran kubectl create deployment nginx-deployment --image=nginx, 
Kubernetes automatically generated a default selector for it 
(typically matching app: nginx-deployment). 
However, in your nginx-deployment.yaml file, 
you defined a different selector (app: nginx). 
In Kubernetes, a Deployment's spec.selector is strictly immutable—once created, 
you cannot modify its selector. 
When kubectl apply tried to update the existing resource with your new selector, 
the Kubernetes API server rejected the request.

How can I solve it?
Since this is a learning/development environment, 
the cleanest and most standard way to transition from an imperative resource 
to a declarative YAML configuration is to delete the old deployment and recreate it using your manifest file.

Step 1: Delete the existing imperative deployment
Run the following command to remove the old conflicting deployment:

$ kubectl delete deployment nginx-deployment

Step 2: Apply your declarative YAML configuration
Now, apply your nginx-deployment.yaml file to create it fresh with your custom specifications (replicas, image version, and labels):

$ kubectl apply -f .\nginx-deployment.yaml

Step 3: Verify the deployment
Check that your deployment is running successfully with the desired configuration:

$ kubectl get deployments
$ kubectl get pods

In Kubernetes, what does it mean that a service is of type 'ClusterIP' ?

In Kubernetes, a service of type ClusterIP (which is also the default service type) means that the service is exposed on a cluster-internal IP address.

Here is what that means in practice:

1. Internal-Only Access
A ClusterIP service is only reachable from within the cluster. 
It is completely hidden from the outside world and cannot be accessed directly from the public internet 
or your local machine's browser (unless you use tools like kubectl port-forward).

2. Cluster-Internal IP Address
When you create a ClusterIP service, Kubernetes assigns it a dedicated virtual IP address (the CLUSTER-IP) 
from the cluster's internal network pool. Other pods and services 
within the same cluster can use this IP (or the service's internal DNS name) to talk to the backend pods securely and reliably.

3. Load Balancing
Even if your service backs multiple identical Pods (replicas), 
the ClusterIP acts as a stable single entry point. It automatically load-balances incoming traffic across all healthy pods matching its selector.

Summary Comparison
ClusterIP (Default): Internal communication only 
(Pod-to-Pod or Service-to-Service within the cluster).

NodePort: Exposes the service on a static port on each node's IP, making it reachable from outside the cluster via <NodeIP>:<NodePort>.

LoadBalancer: Provisions an external load balancer from your cloud provider (like AWS, GCP, or Azure) to route external traffic directly into the cluster.

1. General Metadata

Name (mongodb-service): The name of the Kubernetes Service resource you are describing.

Namespace (default): The virtual cluster partition or namespace where this service lives. 
By default, resources go into the default namespace unless specified otherwise.

Labels & Annotations (<none>): Key-value metadata tags. No custom labels or annotations have been added to this service object.


2. Routing & Type Configuration

Selector:                 app=mongodb
Type:                     ClusterIP

Selector (app=mongodb): This is the most crucial matching rule for the service. 
It tells Kubernetes: "Find any Pod in the cluster that has the label app=mongodb and automatically route incoming traffic to them."

Type (ClusterIP): Specifies that this service is exposed on a cluster-internal IP address. 
It is only accessible from inside the Kubernetes cluster, keeping your database hidden and secure from the outside world.

3. Networking & IP Details

IP Family Policy:         SingleStack
IP Families:              IPv4
IP:                       10.110.35.151
IPs:                      10.110.35.151


IP Family Policy & Families (SingleStack / IPv4): 
Indicates that the service handles standard IPv4 networking rather than dual-stack (IPv4 and IPv6).

IP / IPs (10.110.35.151): The internal virtual IP address assigned to this service. 
Other pods in the cluster can send database queries to 10.110.35.151 
(or use the DNS name mongodb-service), and Kubernetes will handle the routing.

4. Ports and Endpoints

Port:                     <unset>  27017/TCP
TargetPort:               27017/TCP
Endpoints:                10.244.0.7:27017


Port (27017/TCP): The port exposed by the service itself. 
Applications inside the cluster will connect to this service on port 27017.

TargetPort (27017/TCP): The port on the underlying container where the service forwards incoming traffic. 
Here, both the service port and container port are 27017.

Endpoints (10.244.0.7:27017): This is where the magic happens. 
Kubernetes has checked the app=mongodb selector and found an active Pod 
running at internal IP 10.244.0.7 listening on port 27017. 
This proves that your service has successfully linked up with your MongoDB pod!


5. Traffic Policies and Events

Session Affinity:         None
Internal Traffic Policy:  Cluster
Events:                   <none>

Session Affinity (None): Means there is no sticky session configured. 
Requests are distributed across matching pods using standard round-robin load balancing.

Internal Traffic Policy (Cluster): Tells Kubernetes that traffic can be routed to endpoints across any node in the cluster.

Events (<none>): Lists recent Kubernetes lifecycle events for this service. 
<none> means everything is operating smoothly with zero errors, warnings, or restart events.
